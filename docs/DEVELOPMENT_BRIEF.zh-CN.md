# DSH Semantic UI：个人开源项目开发任务书
版本：1.0 · 2026-10-23（北京时间）
项目暂名：dsh-semantic-ui。名称可作常规调整；json-render 主线、个人开源边界和验收标准不变。

## 0. 任务与完成标准

在用户个人授权的 Mac 开发环境中，独立实现、验证并开源一个面向 DeepSeek Harness（DSH）聊天回答的语义 UI 插件：以 json-render 承载受约束的组件描述，优先实现 ArchitectureExplorer、DecisionExplorer、DataChart。

核心目标是让模型在正常提问时选择合适的表达，并让 UI 在真实 DSH 会话中可靠交付、显示、交互与恢复。项目完成包括实现、必要测试、文档、可安装产物及具备条件后的个人 GitHub 发布，不能以方案、脚手架、独立演示或启动回执代替。

按下列里程碑持续推进，不在完成某个阶段后等待常规确认。缺少宿主能力、个人模型接入或发布认证时，完成其他不依赖这些条件的工作，准确记录待验证项与唯一下一步。不要把条件不足说成验证成功。

2. 本项目与公司无关；只用公开项目、公开文档和独立编写的代码。不得读取、复制或参考公司环境中的适配器、组件、配置、测试记录、截图、接口、数据及凭据。
3. 不访问公司服务器，不在公司仓库开发，不创建公司 Action、工单或知识归档。项目进度和证据保存在本仓库自身；不要把开发接到已有工作台、公司业务项目或其他正在执行的 Codex 会话。
4. 示例、测试问题、数据、截图内容均为新编的虚构数据和通用场景。公开源码、包、文档和演示中不出现内部产品名称、公司域名、内部路径或私人环境信息。
5. 使用用户已经授权的个人开发工具与模型渠道，沿用本机当前有效 Codex 配置，不顺带调整全局模型、路由、账号、任务排程或其他项目。常规依赖安装、隔离开发服务、构建和测试属于本任务。
6. 通过正常工具使用授权的个人登录，不打印、复制、提交或向浏览器分发密钥。DSH 模型测试需要独立核实可用的个人接入；Codex 登录状态不能视作可直接复制给 DSH 的 API 凭据。
7. 自有代码优先 MIT。分别保留依赖的 LICENSE、版权与必要 NOTICE；记录实际依赖版本的许可证，不能将所有依赖笼统标为 MIT。
8. 公司环境安装、验证和生产切换由后续使用者完成。本阶段只做个人仓库、本地隔离验证和个人开源发布。

## 2. 产品目标与首版范围

按读者的理解任务选择表达：

- 需要理解架构、依赖、方向和情景传播时：提供可探索的关系图。
- 需要在共同维度和约束下比较方案时：提供有依据、可解释的比较。
- 需要理解数值变化、类别差异或分布时：提供可筛选、可核对数据的图表。
- 简单事实、短解释、没有额外交互收益的回答：直接文字即可。
- 允许简短结论、说明与 UI 同时出现；UI 应减少理解负担，而不是增加卡片数量。

v0.1 只实现三个封闭语义组件、一份版本化协议和薄 DSH adapter。独立演示页仅用于组件开发、排错与展示，其验证结果必须与真实 DSH 验证分开。

不重新开展广泛框架选型；不建设通用组件市场、任意代码应用生成器、工作流平台、第二套模型调用层或第二套聊天会话数据库。

## 3. 上游核实与技术分工

公开参考：

- https://github.com/deepseek-ai/deepseek-harness
- https://github.com/vercel-labs/json-render
- https://github.com/xyflow/xyflow
- https://github.com/dagrejs/dagre
- https://github.com/apache/echarts

开工时核实真实可安装的版本、公开 API 和许可证，记录核实日期、包版本与必要的 commit。当前公开 master 文档只能提供调查线索，不能替代对锁定版本的 import、构建和实际运行验证。

职责保持清楚：

1. 协议与语义层：组件 catalog/schema、版本、语义校验、声明式规则、统计纯函数及可读错误。
2. 组件层：三个 React 语义组件与本地交互。实际使用 json-render 的 catalog/registry/renderer 机制；不能只在项目名称中提及它，再写一套不使用上游的渲染器。
3. DSH 适配层：只处理公开扩展注册、工具参数和结果映射、聊天挂载、宿主事件与支持的状态传递。
4. React Flow 提供节点、边、视口等交互；Dagre 计算初期有向图布局；ECharts 绘图。本项目不重写布局或图表引擎。
5. 结构保持简单。是否拆包取决于实际 DSH 的 host/client 打包要求，不为了架构形式建立大量空包。

json-render 本身不保证语义正确、工具通道正确、DSH 历史恢复或代码安全。上述能力均需本项目实现或验证。

## 4. 第一个里程碑：先证明真实聊天交付链路

优先在固定的公开 DSH 版本上，用一个最小 ArchitectureExplorer 样例证明：

自然问题 → 正确工具调用 → 参数校验 → 可持久化组件载荷 → 原生聊天位置渲染 → 工具过程保持折叠时仍可见 → 刷新、切会话、历史重开仍可恢复。

如果模型接入暂不可用，可先用明确标注的确定性夹具验证宿主链路；它不能计入自然问题模型实测。

必须先确认以下宿主事实，并在简短能力表中链接官方文档或公开源码：

- 原生工具/插件注册与参数机制。
- 最终聊天节点和工具过程卡各自的渲染入口、生命周期、折叠行为。
- 工具结果中哪些数据真实持久化，哪些只存在于本次执行。
- 事件重放、历史补页、刷新和会话切换机制。
- 流式能力或可用的生成状态入口。
- Native tool 与 Code/PTC 嵌套工具调用的差别。

当前公开文档提示应调查 ConversationNodeDefinition、ctx.uiConversation.events.register、conversation.chat.node 和 output.presentationMeta；仅将其作为待在锁定版本核实的候选，不能盲写不存在的接口。

尤其注意：canonical tool value 不等于已持久化的 UI spec；公开文档描述的 presentationMeta 在 nested Code/PTC dispatch 下可能不会执行。对两种调用路径分别确认支持范围，不能把只通过 Native 的结果外推到 PTC。

仅有 tool.call.toolview 或展开工具卡后可见，不满足本任务的聊天呈现要求。不得以扫描 DOM、修改宿主私有内部结构、重写旧消息或第二套会话存储掩盖缺失接口。

若目标公开版本确实不支持某项能力，明确标记并继续完成组件、协议、测试和可安装预览；这项能力保持未通过，不编造兼容配置。

## 5. 统一交付协议与数据边界

1. 以 catalog/schema 为单一事实来源，生成类型、工具参数说明、校验与文档；常驻原则、工具描述和 Skill 必须遵循同一输出协议。
2. 项目协议至少包含协议版本、组件类型、稳定展示标识、语义载荷和可读摘要。DSH envelope 的具体字段按真实公开 API 决定，不能猜测。
3. 定义展示标识的生成、同标识更新、重放去重和版本不支持时的行为。历史重放不能产生重复图，也不能静默换义。
4. 组件参数只接受白名单纯数据。禁止模型生成的 JavaScript、JSX、字符串表达式执行、任意 callback、任意 ECharts option 或不受限 HTML。
5. 约束组件类型、动作、URL 协议、外部资源、spec 字节数、嵌套深度、节点/边/数据行数量及计算量。限制值由实测和目标场景决定并记录。
6. 同时做结构与语义校验：ID 唯一性、关系引用、路径有效性、比较维度对应、数字合法性、类型与单位、统计口径。
7. 错误应包含稳定错误类别、字段路径、可读原因及修正提示；模型可修正，用户可见。前端有错误边界和可读降级内容，不静默空白。
8. 输出摘要与 UI 载荷分离，避免把完整 spec 再返给模型或重复贴在正文；保留足够的信息帮助模型解释结果和修正错误。
9. 明确生成中、已完成、无数据、验证失败和渲染失败状态。没有真实增量 spec 能力时提供准确的生成状态，不伪装流式内容。

## 6. ArchitectureExplorer

模型输入：稳定节点、真实有向/无向关系及语义、职责、约束、情景路径和必要依据。组件负责布局、缩放、聚焦、详情和情景高亮。

要求：

- 节点和边有稳定 ID，边保留方向、类型和需要的标签；不能为布局好看删边、补边、伪造层级或抹掉环路。
- 情景只能引用输入中实际存在的节点与边；验证路径连续性和方向，缺失时显示具体问题，不补造路径。
- 聊天宽度下首屏能看懂主关系。节点显示简短标签，长职责、约束和依据放详情区，不能退化为长文字卡片墙。
- 较大样例先提供概览、邻域聚焦、搜索/定位和必要的展开；记录实际验证的规模边界。
- Dagre 首版用于适合它的扁平有向图；复杂嵌套分组及跨子图连线如受限应明确说明，不在首版引入多套布局引擎。
- 交互不能改变原始架构事实。筛选隐藏了哪些节点/边应清楚可知，并能恢复全图。
- 附文本关系清单或等价可访问说明，方便核对与键盘使用。

## 7. DecisionExplorer

模型输入：方案、共同维度、优缺点、适用条件、硬约束和依据；必要时提供有限的声明式条件规则。

要求：

- 用共同维度对齐方案；不对缺失信息自行补齐，不把未知当零分。
- 支持选择关注维度、查看约束和展开依据。仅改变展示维度，不能暗中改变推荐。
- 条件改变会影响推荐时，采用有限、确定性的规则：明确允许的比较操作和布尔组合、规则优先级、冲突、无匹配和缺少输入时的处理。
- 推荐结果显示触发了什么规则、依据是什么、哪些条件发生变化。规则是模型基于输入提出的判断时，明确区分它与用户给定事实。
- 不执行脚本或任意表达式；不凭空创造评分、权重、胜率或精确排名。
- 允许并列推荐、条件不足或无法区分；不强求唯一赢家。
- 纯本地操作不得假装调用了模型重新分析。若支持回传，以明确操作触发并显示真实状态。

## 8. DataChart

v0.1 图型明确为折线图、类别柱状图和直方图。暂不建设通用统计引擎。

要求：

- 支持适合该数据的区间筛选、系列开关和原始数据表核对，图形与表格来自同一份确定的数据源。
- 区分缺失/null、零和负数；禁止用零填充缺失、静默丢弃负数或使用不合法对数轴。时间轴说明时区、粒度与排序策略；保留单位。
- 原始数据表区分全量、筛选后与派生数据，显示当前范围、有效样本数、缺失量及必要口径。
- 直方图接受原始观测值或明确的预聚合区间；给出分箱边界、边界包含规则、计数/比例含义、有效样本数。多组分布比较使用可比的分箱。
- 类别频次或排序柱状图仍是类别柱状图，不能称直方图。
- 比例需要分子、分母和聚合范围；加权平均需要权重及公式；分位数需要算法/估计方法或明确的外部提供方。不具备口径时拒绝相关计算或标为未知。
- 统计计算放在独立可测的纯函数中，ECharts 只接收确定的绘图配置。为缺失、全零、负数、边界值和空筛选等实际风险设置必要测试。
- 不让组件编造结论。筛选后不能继续无提示地展示只适用于全量数据的固定结论；可以保留“基于原始全量数据”的解释，或只展示确定性更新指标。
- 表格、图例、轴标签、tooltip 与窄屏布局可读；颜色不作为唯一信息编码。

## 9. 表达选择与按需说明

常驻指引应简短，可采用下列含义：

“先判断读者要理解关系、比较取舍还是分析数值。只有交互能明显帮助完成理解任务时，才选对应语义组件；简单问答直接文字。需要 UI 时，通过本插件唯一工具入口提交参数，正文只保留结论与必要说明，不输出组件 spec 或 JSON/JSONL 围栏。字段细节按需查看组件说明；未知事实和口径不得补造。”

实现要求：

1. 常驻层让模型知道三个能力、适用任务和正确通道；详细字段、长示例、操作说明按需提供，不将入口藏到模型无法发现。
2. 核实 DSH 实际如何注入工具 schema。大型 schema 若自动常驻，不能靠口头声称“按需加载”；记录实际注入内容和 token 开销。
3. 根据测量选择简短 envelope + 按需说明 + 严格 runtime validator，或其他锁定版本真实支持的设计；保留模型可修正性。
4. 不原样注入 json-render 默认 catalog.prompt() 后再追加相反要求。当前上游 standalone 要求输出 JSONL，inline 会混合正文和 JSONL；工具交付模式需生成专用于工具参数的说明，或核实后完整替换输出模板。
5. 使用唯一插件前缀命名工具与 Skill，不注册 genui 等会与其他插件冲突的同名 Skill。
6. 为常驻提示、生成 schema 说明、工具描述和 Skill 做一次有针对性的合同检查，防止输出通道指令互相矛盾。
7. UI 未出现时分别诊断：文字确实更适合、表达选择遗漏、通道错误、参数不合法、工具执行失败、前端挂载失败、历史恢复失败。不能全部归因于提示词。
8. 不用字数、条目数或固定出图率作为选择 UI 的强制阈值。

## 10. 状态、历史与 GenUI 兼容

分别说明并验证以下能力，不能合称“支持持久化”：

| 能力 | v0.1 要求 |
| --- | --- |
| 内容恢复 | 从 DSH 已保存的消息/工具事件重新显示相同组件；真实宿主验证为必需 |
| 本地交互 | 节点选择、关注维度、筛选等在当前 UI 生效 |
| 刷新后的交互状态 | 明确保留或复位；若使用本地存储，只存可丢弃的显示偏好，并按宿主/会话/消息/组件隔离 |
| 状态回传模型 | 仅实现公开 API 真实支持的方式；未支持时明确操作不会让模型重新分析 |
| 跨设备同步 | 不默认承诺，未实现则明确不支持 |

不新增聊天记录库，不持久化第二份完整会话。历史组件版本不支持时给出可读说明，不能篡改原消息。

GenUI 必须先落实到具体公开仓库、包名和版本。公开已有 dsh-ui 围栏/声明组件型与生成 React/TS 应用型实现，不能视作同一种协议。候选公开参考：

- https://github.com/omdsh-dev/dsh-genui
- https://github.com/pengyue-polaron/deepseek-harness-genui

分别核实：

1. 新回答如何优先使用本插件，如何关闭重复生成指引或冲突工具。
2. 旧 GenUI 消息如何继续由原 renderer 显示。
3. host 引导、Skill、工具和 client renderer 是否可通过公开方式分别启停。
4. 安装、并存、停用与回退是否需要重新加载宿主，是否影响已存消息。

不能发明 injectPrompt 等未经核实的配置；关闭某一个工具不等于关闭所有注入。若无法分离历史 renderer 与生成引导，记录准确限制及可行共存方式，不以卸载旧插件或改写旧消息冒充兼容。

没有可读取的个人目标环境包名时，选择一个明确的公开版本做兼容研究并标注测试对象；不得借此读取公司配置。涉及用户现有 GenUI 的兼容结论保持待验证。

## 11. 真实验证与样本保留

在调优之前固定 11 道自然问题：架构 3 题、方案比较 3 题、数据分析 3 题、适合文字的简单问答 2 题。全部虚构场景，不含“画图、可视化、交互界面、使用某组件”等表达要求。

设计题目覆盖：

- 架构：依赖、失败/情景传播、带约束的服务关系。
- 比较：共同维度、条件变化、信息不足或无唯一赢家。
- 数据：趋势、缺失/零/负数、分布与统计口径。
- 对照：文字足以回答的短事实或解释。

每题预先注明理解任务与事实核对标准，允许多种合理表达；不把调用组件当作唯一正确答案。

至少两轮完整运行：

1. 第一轮保留全部首次结果、模型可见输入、实际工具调用与浏览器结果。
2. 记录失败归因、修复内容和代码/提示版本。
3. 第二轮用同样问题完整复测，保留所有成功和失败。
4. 两轮保持模型渠道、模型标识、可控设置一致；记录无法控制的版本/采样因素。
5. 每题用新的测试会话，避免前题或人为引导污染。任何重试单独记录，不替换首次失败。不用筛出的最好结果当整体表现。

逐题检查：表达合适程度、理解收益、交付通道、真实显示、控件改变内容、数据/关系/结论准确性、窄屏阅读体验。

代表性三组件另跑宿主生命周期矩阵：生成中、完成态、工具过程持续折叠、刷新、切会话、历史重开和历史补页。至少验证正常聊天栏约 640px 与窄屏约 360px 的实际容器，并记录实际尺寸；全屏演示不能替代。

记录和诊断保持轻量，不建设通用评测平台。schema 通过率、控制台错误数、组件数量与出图率只能作诊断，不是用户价值验收。

优先在隔离的本地真实 DSH 中运行。没有个人模型接入时仍完成组件、公开 API、回放、构建和安装检查；把自然提问模型测试标为未执行，不使用虚构结果、不把 mock 或独立网页称作真实 DSH 验证。

## 12. 实施顺序

- M0：核实个人目录/Git/GitHub，锁定上游与 DSH 版本，输出简短能力表和协议草案。
- M1：跑通最小纵向聊天交付与恢复链路；如果外部条件阻塞，准确记录后并行完成不依赖它的组件工作。
- M2：完成三组件、严格校验、明确交互与错误状态、统一按需指引。
- M3：完成真实 DSH 生命周期矩阵及两轮自然问题；所有未通过项保留证据。
- M4：完成文档、版本化安装包、校验和、许可证，并在个人身份和权限确认后公开发布。

只做能解决具体风险的验证，满足当前验收后停止额外扩张。不得以“阶段完成”当整个项目完成；同时不因单一外部条件缺失停下全部独立工作。
