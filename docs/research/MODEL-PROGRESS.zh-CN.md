# 产品价值与模型进步

日期：2026-10-23。本文是产品判断与待验证假设，基于 `0.1.0-preview.5` 及公开研究；不承诺未来需求、商业成功或长期不可替代。文档建议不等于新增能力已经发布。

## 现实判断

生成图表配置、漂亮页面、简短组件代码和常见示意图，都可能随模型进步而变得更便宜、更普及。如果产品的主要收益来自弥补这些能力缺口，就应当预期价值受到挤压。静态生图也不是本插件当前的核心交付；模型能画图、能生成可交互代码，以及用户能持续完成任务，是不同的验收对象。

不能用“模型永远不擅长状态/权限/计算”建立路线。模型可以生成相关代码，模型厂商也能把运行时、数据连接、权限和持久化直接做进产品。即使这些能力仍有需求，用户也可能选择内置方案。

[A2UI catalogs](https://a2ui.org/concepts/catalogs/) 已描述组件目录协商、版本与客户端渲染；[MCP Apps](https://modelcontextprotocol.io/extensions/apps/overview) 已覆盖聊天内交互、双向通信与宿主隔离。GenUI 也已有状态与产物机制，见 [吸收范围](GENUI-ABSORPTION.zh-CN.md)。因此，“有交互”“有状态”“有协议”都不足以单独形成独特优势。这些事实支持互通和可替换设计，不能预测哪种标准或产品会胜出。

## 值得检验的定位

目标可以收敛为：**帮助用户把一轮解释变成可核对、可修改、可继续使用的交互结果。** 模型升级后，用户应能直接获得更好的生成和理解能力，同时保留已经确认的数据、条件、选择与历史结果。

| 价值假设 | 对用户的具体意义 | 当前证据与缺口 |
|---|---|---|
| 声明与求值分开 | 看得出哪些是原始输入、模型假设、缺失条件与规则计算 | 有 schema、统计纯函数和 decisionFacts；模型拟定规则与正文仍可错，尚无完整事实核验 |
| 用户修改进入后续任务 | 改一个条件、确认一次选择，下一轮按真实提交继续 | 当前只有本地试算；RequestForm、接受收据和反馈未实现 |
| 结果能长期继续使用 | 重开历史、恢复版本、带着结果迁移，而非重新生成同一个页面 | DSH 内容恢复已验证；本地偏好、跨宿主产物与迁移未实现 |
| 用较少操作完成一个具体任务 | 方案比较/数据解释从查看走到收集缺口、修改、确认 | 目前缺闭环，也没有证明优于最新原生方案的对照 |
| 维护者和使用者共同改善质量 | 可复现失败、清楚兼容范围、可维护扩展吸引外部使用 | 已公开源码与失败证据；真实复用、贡献和持续使用尚未验证 |

这些是需要逐步证明的收益，不是已经建立的护城河。所有能力都可以被其他项目实现；优势来自持续满足真实任务，以及集成、维护、可信记录与使用习惯的积累。开源的可审查和可迁移可以降低采用阻力，但代码可复制，不能由此推导收入或竞争壁垒。私人数据由用户控制，不以锁住数据制造优势。

## 下一步聚焦一条完整工作流

先选现有比较任务：用户给几个方案，模型标出已知事实和缺失条件；用户通过有限表单补充或明确“不知道”；程序重算已声明规则；用户保存一个带输入、假设、结果和版本的决定，并能继续修改。

这个流程直接对应当前 D2/D3 的过早倾向和错误附加解释。应当先核对规则是否忠实于用户输入，再处理展示效果。遇到缺条件时呈现 unknown/insufficient，不能靠精确的计算把错误前提包装成正确结论。用户确认也只说明用户接受了某些输入，不自动认证外部事实。

执行顺序：

1. 补 RequestForm 与宿主接受收据。编辑、提交、已接受、模型继续和失败重试分别有真实状态；处理重复提交和旧版本。保持 DSH 为会话事实源，沿用 [已有合同](ADOPTION.zh-CN.md)。
2. 补来源/假设与用户修正的关联，提供能复算的结果快照。外部来源存在、被引用与被核实分别表达；不让模型自报来源变成认证。
3. 为真实需要设计导出/导入与版本迁移。先证明同一任务能带着内容和确认状态继续，再考虑 MCP Apps/A2UI 的适配。先做一个有用户需求的适配，不同时维护所有协议。
4. 根据任务证据追加表格、散点等表达。继续复用成熟绘图库，让 renderer 可替换；不以控件总数、炫技效果或包装更多图表库作为完成标准。

该顺序是建议，不是全部功能已获验收；现有三组件的失败记录继续保留。

## 如何判断插件仍然值得存在

在后续主要模型升级或重大插件迭代时，做同题对照；本次没有新建定时任务或自动调用。

- 基线同时考虑“模型及其原生产品能提供什么”和“同一模型接入我们的插件”，不故意把基线限制成纯文本。两边获得同一份有权限使用的数据、任务目标和合理工具；平台差异/不可比部分单列。
- 延续冻结的 11 题作为回归，另补完整工作流中的缺条件、修改、刷新、历史恢复与重复提交。用新任务检查泛化，避免只针对已知题优化。
- 保留首次输出、内部修正和全部调用成本；对关键案例重复运行。将内容正确性与界面可用性分开评分，条件允许时隐藏方案名称进行人工判断。
- 比较任务完成率、人工修正次数、总用时、总请求/费用、重开恢复情况，以及换模型后能保留多少有效工作。技术正确性用确定性断言验证；“用户愿不愿继续用”需要真实使用证据。
- 在运行前约定本批任务的合格标准和可接受成本。当前没有足够样本报告这些收益的统计优势，不能用一次成功展示代替对照。

如果连续可比评估中，原生产品在关键任务上做到同等或更好，用户也没有独立集成、可迁移或本地部署需求，就收缩重复的渲染功能：保留仍被使用的评测、语义求值或转换工具，必要时结束该模块维护。不要靠更换宣传词掩盖价值消失。

## 投入原则

短期把主要精力用于一个真实任务的完成闭环、语义正确性和可恢复结果；保持模型与渲染器可替换。生成能力越强，越应减少手工补丁和冗余封装。项目是否继续扩大，以用户完成任务的收益和持续使用为依据；对“永远不会被模型或平台替代”不作保证。
