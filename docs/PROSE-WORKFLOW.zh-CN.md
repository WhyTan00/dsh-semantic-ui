# 工作流正文：条件、动作与分支范围

[下载 prose.2 客户端与校验和](https://github.com/WhyTan00/dsh-semantic-ui/releases/tag/client-v0.1.0-preview.31-prose.2)

在现有 **“核对说明与来源”** 面板直接输入工作流来源和候选正文，或选择含这两段文字的 JSON。新增路径复用已有完整工作流来源检查器，不用当前图表替来源背书，也不把正确的来源说明当作候选正文已经通过。

例如来源为：

> 入口→鉴权→库存→支付，支付→通知；通知失败只重试通知，不回滚支付。

本次真正核对了原 A2 首次失败正文，而没有再次请求模型。它自己的“通知失败只重试通知、不回滚支付”得到支持；“库存之后支付和通知都无法到达”“上游已经完成”“通知阻碍回传”缺少执行或传播依据，分别定位并生成有限修订。原文正确部分与无据部分分开，不把整段都标未知，也不删除原文。

## 可以核对的具体含义

| 候选说明 | 有限核对 |
|---|---|
| 通知失败时。此时仅重试通知。此分支不回滚支付。 | 条件沿相邻句绑定，两个局部规则获得支持 |
| 通知失败后，重试整个流程。 | 与明确的仅重试通知范围矛盾 |
| 通知失败时，支付会被回滚。 | 与此分支不回滚支付矛盾；支持对象在动词前的有限被动改写 |
| 通知失败时，不是不回滚支付。 | 处理双重否定，仍与该分支规则矛盾 |
| 库存失败时，不回滚支付／补偿支付。 | 来源没有此分支策略，依据不足；不借用通知规则 |
| 通知成功时，不回滚支付。 | 否定或不同触发条件不等于失败分支，不能由它批准 |
| 通知失败时。如果负载增大，只重试通知。 | 新条件未绑定，不沿用先前失败条件 |
| 通知失败时。日志故障。此时只重试通知。 | 无法解析的新话题撤销旧条件，指代保持未知 |
| 重试三次直到成功。 | 来源未给次数、最终状态或必成功保证 |

支持有限的主动／被动动作、单重／双重否定、完整节点名称及局部和整流程范围。节点按来源字面名称完整绑定：“通知”不会被用来猜“邮件通知”，“支付”不会被用来猜“支付系统”。合并触发条件、必要条件与无条件全局保证不会自动继承单一分支政策。

段落、新触发分支、未能绑定的新条件或新话题会结束旧条件的作用范围。只有相邻且能够沿有限语法绑定的说明才共享上下文。未识别的文字仍单独保留。纯拓扑中末端节点的出边可以核对，但不据此推导实际故障只影响某段、反向回传或上游已经完成。

“补偿策略未知”不能批准后面的“但会补偿支付”；其他指标未知也不能给确定的执行断言背书。首次新增反例曾发现旧条件被带到未识别故障、负载条件和成功路径；原失败记录保留，随后修正并补了反例。

每项都保留候选逐字片段／位置、条件来自哪句、动作对象和极性，以及来源 SHA-256、相应失败规则及字节范围。`src/prose-workflow.ts` 只是正文到既有 `checkSourceWorkflow` 的有限适配，原工作流来源语法和求值不重写。`src/prose.ts` 沿同一入口生成有据说明。

## 使用与历史

修改来源即清除旧结论。把通知失败的“只重试通知”改为“只重试支付”时，同一候选的重试结论会由支持变为矛盾，说明也按新来源更新。旧导出仍记录原来的来源；重新打开会按它自己的来源重新核对，不覆写新的或旧的会话历史。

客户端增量为 **`0.1.0-preview.31-prose.2`**，兼容原31宿主，以及原31客户端或已接受的prose.1。安装器识别被接受的旧客户端摘要，升级前备份；回退恢复升级前的实际客户端，而不是一律退到最早原31。运行配置与宿主不变。安装方式见 [说明核对与客户端增量](PROSE-REVIEW.zh-CN.md)。

正常个人 DSH 的必要差异已验证：选择原A2来源与正文、看支持与无据句及修订、跨句条件、改变来源动作对象后重新判断、原导出独立恢复、整流程重试／支付被回滚／未知库存补偿，以及未识别新条件不借旧分支；pageerror为0。类型检查、67项针对性检查（含原有核心回归）和4项安装隔离／升级回退检查通过；未重做旧中文、入口、下载或CI矩阵。见 [接受回执](evidence/prose-workflow.json)。

原自然六题仍是 **0通过／6失败／18请求**。本次新增模型、MCP连接、服务和远端CI任务均为0；不拦截组件外其他assistant或GenUI正文，不认证任意开放语义、身份权限或世界事实，也未新增Codex原生富UI、Linux/PTC、用户Edge视觉或物理手机接受。
