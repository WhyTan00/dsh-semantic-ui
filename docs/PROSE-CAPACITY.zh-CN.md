# 容量正文：当前、未来、可能与所需量

现有 **“核对说明与来源”** 面板现在接收完整的有限容量来源和候选正文。它复用 `checkSourceCapacity`、`capacityDecision` 和 `decide`，从同一来源核对文字、字段角色与容量条件，不能用正确图表给错误时间或整体选择背书。

| 来源字段 | 表示什么 | 不能被改写成 |
|---|---|---|
| 方案容量上限 | 来源声明可提供量的上限 | 现在已拥有／已预留的实际容量、未来能力承诺 |
| 当前需求 | 现在所需量 | 当前已拥有量、未来可能点 |
| 未来可能需求点 | 可能出现的所需量 | 当前需求、未来已有容量、必然发生或已确认计划 |
| 已确认未来计划 | 当前有限来源合同中保持 `null` | `false`、肯定承诺、确定日期或默认预留政策 |
| 明确本地需求假设 | 用于独立容量试算 | 已修改原始需求或已执行预留／扩容 |

原D2来源的80GB是**当前需求**，300GB是**未来可能需求点**，100GB／1000GB是两个方案的容量上限。即使数值相同，也不能把“未来可能需求300GB”写成“未来可能拥有300GB”；未承诺的未来提供能力仍没有依据。

## 真正核对候选正文

原D2全文中的80／300两个明确需求情景可用现有核心核容量条件；它的“两个阶段的客观分界”会单独标明没有建立确定时间阶段，不能把需求示例升为已确认未来。容量达标也不能建立“只有B可选”、必须承受维护成本或未经核实的预留控件承诺。原正确部分、无据部分和未覆盖文字分别保留，不改写原模型记录或原自然题分数。

- “当前需求不是80GB”“当前需求不等于300GB”按明确极性与当前字段核对；不从未知推否定。
- “未来可能到300GB。届时A容量不足。”只在该需求假设下核容量；“现在A容量不足”另按原始当前需求计算。
- “以后可能到300GB。这个计划／阶段已确定。”不能从可能点得到确认；日期也不能由没有日期的来源补出。
- “假设需求200GB”会把独立局部试算写入有据说明，保留原始当前需求和未确认未来。
- “已按300GB预留”和“不按300GB预留”都不会被误读成正向300GB需求假设。
- 同句多个上限各绑定最近的明确方案；已知方案名不会靠子串猜另一方案。
- 容量条件不能认证安全、性能、所有需求或整体最优；部署与维护分别核对，未知维护不补成简单，复杂也不自动成为价格或必付成本政策。

每项保留候选原句／位置、来源SHA-256、时间和数量角色、条件来处、字段／规则与来源字节位置。`src/prose-capacity.ts` 负责有限映射，求值沿既有核心；没有另写容量算法、修改原始unknown或增添模型评审。

当前完整来源语法只覆盖既有的两上限、当前需求、可选未来可能需求点和独立部署／维护声明。来源若包含未支持的明确未来承诺或日期，整个来源会拒绝，而不是丢弃那句后悄悄说成null。开放隐喻、无从消歧的指代和任意世界事实不在合同内。

## 来源更新与正常面板

已用一组新的公开合成来源验证：小盘上限60GiB、大盘上限500GiB、当前需求100GiB、未来可能需求240GiB。把小盘上限改成120GiB后，同一句“小盘当前容量不足”由支持变成矛盾，当前来源说明显示它已满足容量；未来240GiB仍只是独立假设，仍不足。旧导出按原60GiB来源独立重新核对，旧记录和null／unknown不被覆盖。

这是**现有个人DSH面板的确定性工程接受**，不是新模型生成或自然选择工具的观察。原D2完整正文、当前不足→来源更新足够、实际拥有／未来确定／未来提供量／整体要求的反例和旧记录独立恢复均在正常面板通过，pageerror为0。类型检查及91项针对性检查（含受影响的既有工作流／容量核心回归）通过，未重做旧中文、入口、下载或CI矩阵。

8个新增开发反例首次失败记录保留：多上限错绑、将当前上限投射未来、已预留／否定预留的假设误判、安全需求的容量冒认、有据说明漏独立假设、阶段抬升和未来提供量角色遗漏。修正后重新验证，不用最初的绿灯覆盖后续反例。
