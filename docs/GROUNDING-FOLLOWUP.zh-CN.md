## 两种方向不同的布尔关系

`supports`：选项是否支持某能力，输入表示用户是否需要该能力。例如“支持私网”对“需要私网”。输入false时不要求该能力；输入true时不支持者失败。

`requires-availability`：选项是否需要某资源，输入表示用户是否具备该资源。例如“需要团队维护”对“团队有维护余力”。不需要团队维护的选项不会因为用户有团队或没有团队而被排除；需要维护时，用户明确没有余力才失败，未知余力保持未知。

| 选项需要资源 | 用户具备资源 | 检查状态 |
| --- | --- | --- |
| false | false / true / null | inactive：无需该资源 |
| true | false | fail |
| true | true | pass |
| true | null | unknown |
| null | false / true / null | unknown：保留源事实不明 |

这是显式合同，**不是自动理解或认证原话**。模型仍可能选错关系或编造维度；两种关系不能靠中文/英文标签的关键词偷偷互换。新关系只允许协议1.3，历史1.2的supports含义保持不变。

原run9-D1的结构与错误结果完整保留。确定性修正夹具只改变“需要维护”那一条关系：余力true时两者可行，false时排除虚拟机，null时托管平台可行、虚拟机未知；不产生偏好推荐。不涉及原回答中费用单位、维护范围等其它错误的认证。

## 条件实际改变什么

程序从requirements直接输入及激活条件、constraints和rules计算`inputEffects`，分别列出影响的ID和hard / preference-only / hard-and-preference / unused范围。偏好专用控件旁显示“只探索偏好，不改变硬性可行性”，并提供可展开的声明映射。

原run9-D2的reserveNow只连偏好规则。需求50GB时勾选该项不会自动变成300GB硬需求，现明确展示这一点；模型若声称它会排除A，正文仍是错误。单独调整需求容量才能检查50/80/300GB；只有显式连接容量要求的激活条件才影响硬性判断。没有替模型暗改原日志或补造未来已确认的计划。
